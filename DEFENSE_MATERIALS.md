# TaskFlow: Материалы для защиты проекта (Курс ООП, 2 семестр)

Данное руководство содержит исчерпывающие материалы для защиты бэкенда перед преподавателем и экзаменационной комиссией: концепцию, архитектурные обоснования, пошаговый демо-сценарий и готовые ответы на сложные технические вопросы.

---

## 1. Концепция и архитектурный обзор

### 1.1 Бизнес-проблема и цель
Большинство существующих решений фрагментированы: команды ведут задачи в Jira/Trello, время учитывают в Toggl/Clockify, привычки отслеживают в мобильных приложениях, а заметки пишут в Notion. **TaskFlow** объединяет эти процессы в единую экосистему для небольших продуктовых команд и индивидуальных специалистов.

### 1.2 Выполнение критериев преподавателя
1. **Количество сущностей:** **18 таблиц** (нормализованы до 3НФ). Из них **10 объектов реального мира**:
   - `User`, `Workspace`, `Project`, `Task`, `Comment`, `Milestone`, `Note`, `Habit`, `Attachment`, `Notification`.
   - Служебные и связующие сущности: `WorkspaceMember`, `Label`, `TaskLabel`, `TimeEntry`, `HabitCheckin`, `ActivityLog`, `RefreshToken`, `NotificationSetting`.
2. **Клиент-серверное разделение:** Бэкенд реализует строгий, версионированный REST API контракт (`/api/v1`) с OpenAPI-спецификацией ([`openapi.json`](openapi.json)) и документацией ([`API_CONTRACT.md`](API_CONTRACT.md)).
3. **Технологический стек:** **FastAPI**, **PostgreSQL 16** (asyncpg + SQLAlchemy 2.0 async), **Redis 7** (кэш, blacklist, rate-limit, pub/sub, arq).
4. **Бюджет ресурсов (Arch Linux, 8 ГБ ОЗУ):** Суммарное потребление памяти сервисами ограничено в `docker-compose.yml` на уровне **~1.5 ГБ** (App: 512MB, DB: 512MB, Redis: 256MB, Worker: 256MB). Никаких тяжеловесных JVM-сервисов (Elasticsearch, Kafka).
5. **Слоистая архитектура:**
   ```
   [API Routers & Deps] ──> [Service Layer] ──> [Repositories] ──> [SQLAlchemy Async Models & DB]
           │                         │
           ▼                         ▼
   [Pydantic v2 Schemas]      [Redis / ARQ Worker / Telegram]
   ```

## 2. Разбор ключевых алгоритмов и решений (технический базис)

### 2.1 Оптимистичная блокировка (OCC via `version`)
- **Проблема:** Два менеджера одновременно открыли задачу и нажали «Сохранить». Без блокировки изменения второго перезапишут изменения первого («lost update problem»).
- **Решение:** В таблице `tasks` есть целочисленное поле `version`. При изменении выполняется запрос:
  ```sql
  UPDATE tasks
  SET title = :new_title, version = version + 1, updated_at = now()
  WHERE id = :task_id AND version = :expected_version AND deleted_at IS NULL;
  ```
  Если `rowcount == 0` — версия изменилась, сервис возбуждает `VersionConflictError` $\to$ HTTP 409 Conflict. Клиент предупреждается о конфликте без блокировки строк в БД.

### 2.2 Предотвращение циклов в дереве подзадач
- **Проблема:** Пользователь делает задачу $A$ подзадачей $B$, а затем $B$ назначает подзадачей $A$. Возникает бесконечный цикл обхода.
- **Решение:** В [`TaskRepository.would_create_cycle`](file:///home/opium/.agy/university_app/app/repositories/task.py) реализован алгоритм проверки предков: перед сохранением нового `parent_id` сервис итеративно поднимается по цепочке предков кандидата в родители. Если в цепочке встречается текущий `task_id` — операция блокируется с ошибкой `422 Unprocessable Entity` (`CyclicDependencyError`).

### 2.3 Принцип 404 вместо 403 при доступе к чужим пространствам
- **Безопасность:** Если пользователь $A$ пытается открыть `GET /workspaces/{uuid_b}`, возвращается **404 Not Found**, а не 403 Forbidden. Это предотвращает атаку типа enumeration (перебор UUID с целью выяснить, существует ли в системе закрытая команда с таким идентификатором). 403 возвращается только когда пользователь подтверждённо состоит в пространстве, но его роль недостаточна для действия.

### 2.4 Аппаратное ограничение активного таймера в БД
- **Проблема:** Race condition: пользователь быстро нажимает «Старт» в двух вкладках браузера. Проверка в приложении `if active_timer:` может пропустить оба запроса до коммита транзакции.
- **Решение:** Частичный уникальный индекс на уровне PostgreSQL:
  ```sql
  CREATE UNIQUE INDEX ix_time_entries_user_running
  ON time_entries (user_id)
  WHERE is_running = true;
  ```
  Физически невозможно иметь более одной незавершённой записи времени на пользователя.

### 2.5 Real-Time архитектура через Redis Pub/Sub
- При публикации комментария с `@username` или наступлении дедлайна бэкенд сохраняет запись в БД и отправляет событие в Redis-канал `notifications:{user_id}`.
- Сервер FastAPI слушает этот канал и пересылает JSON-сообщение в WebSocket клиента. Сервер остаётся **stateless**: если запустить 10 инстансов бэкенда за балансировщиком, уведомление всё равно дойдёт до нужного сокета независимо от того, к какой именно ноде подключен браузер.

## 3. Сценарий живой демонстрации (5-минутный план)

| Шаг | Действие | Что показать преподавателю |
|---|---|---|
| **1. Запуск и Swagger** | Открыть `http://localhost:8000/api/docs` | Показать группировку тегов, аккуратные описания, схему моделей и единый формат ошибок. |
| **2. Демо-данные** | Зайти в БД или через API `GET /workspaces` | Показать предзаполненные сид-данными сущности (Alice - Owner, Bob - Member, Charlie - Viewer). |
| **3. RBAC в действии** | Запрос от лица Charlie (Viewer) на создание задачи | Получаем `403 Forbidden` с сообщением: *"Action requires 'member' role or higher in this workspace"*. |
| **4. Конкурентное редактирование** | Отправить `PATCH /tasks/{id}` с устаревшей `version: 0` | Получаем `409 Conflict` (`VERSION_CONFLICT`). Показать, что данные защищены от затирания. |
| **5. Циклические подзадачи** | Попытаться назначить задачу родителем самой себя | Получаем `422 Unprocessable Entity` (`CYCLIC_DEPENDENCY`). |
| **6. Учёт времени** | Запустить таймер `POST .../time-entries/start` дважды подряд | Первый запрос возвращает `201 Created`, второй — `409 Conflict` (`TIMER_ALREADY_RUNNING`). |
| **7. Привычки и стрики** | Попробовать отметиться в привычке дважды за одну дату | Получаем `409 Conflict`. Показать `GET /habits/{id}/stats` с расчётом стрика и процента выполнения. |
| **8. Real-Time WebSocket** | Подключиться к `ws://localhost:8000/api/v1/ws/notifications?token=...` | Отправить комментарий с `@bob`. В WebSocket мгновенно падает событие `notification.new`. |

## 4. Ответы на вероятные вопросы преподавателя

### В1: Почему выбран стек FastAPI + asyncpg, а не привычный Django?
> **Ответ:** Django ориентирован на монолиты с server-side рендерингом (Django Templates/Admin). В нашем ТЗ фронтенд пишется отдельной командой на React, поэтому ключевые требования — производительность API, автоматическая валидация схем через Pydantic v2 и нативная асинхронность. FastAPI на базе ASGI и `asyncpg` даёт минимальный оверхед по памяти (важно для ноутбука с 8 ГБ) и легко держит тысячи одновременных WebSocket-соединений, что на синхронном Django WSGI потребовало бы сложных надстроек вроде Channels и отдельных процессов Daphne.

### В2: Почему для фоновых задач выбран arq, а не традиционный Celery?
> **Ответ:** Celery избыточен для учебного проекта: он требует тяжёлых зависимостей (Kombu, billiard), ориентирован на AMQP (RabbitMQ) и потребляет значительно больше ОЗУ. `arq` построен на базе `asyncio` и нативного Redis (который уже есть в нашем стеке), весит считанные мегабайты, прозрачно выполняет асинхронные корутины и потребляет менее 100 МБ памяти, идеально вписываясь в наш лимит ресурсов.

### В3: Почему вы использовали Argon2id вместо bcrypt или SHA-256?
> **Ответ:** SHA-256 не является алгоритмом хеширования паролей — он быстрый и легко ломается на GPU/ASIC перебором с миллиардами хэшей в секунду. `bcrypt` хорош, но уязвим к оптимизациям под GPU и ограничен длиной пароля в 72 байта. `Argon2id` — победитель Password Hashing Competition (RFC 9106): он обеспечивает защиту не только по вычислительной сложности (time cost), но и по памяти (memory cost: 64 МБ), делая параллельный подбор на видеокартах экономически нецелесообразным.

### В4: Что произойдёт, если сервер Redis аварийно перезагрузится?
> **Ответ:** 
> 1. В `docker-compose.yml` для Redis включено сохранение на диск (`--save 60 1` и volume `redis_data`), поэтому критичные данные (токены) восстанавливаются при старте.
> 2. Источником правды для refresh-токенов является таблица `refresh_tokens` в PostgreSQL. Если токен временно выпал из кэша Redis, сервис авторизации делает fallback-запрос в PostgreSQL.
> 3. WebSocket-клиенты автоматически переподключатся к каналу pub/sub при восстановлении соединения.

### В5: Как работает полнотекстовый поиск и почему именно `tsvector` в PostgreSQL?
> **Ответ:** Введение отдельного поискового движка (Elasticsearch) на машине с 8 ГБ ОЗУ вызвало бы Out-Of-Memory (Elasticsearch требует от 2-4 ГБ heap). PostgreSQL имеет встроенный FTS движок: при сохранении задачи или заметки триггер автоматически преобразует текст на русском языке в лексемы через стеммер (`to_tsvector('russian', ...)`). Запросы выполняются через GIN-индекс за миллисекунды без накладных расходов на синхронизацию внешней базы данных.

### В6: В чём преимущество UUID перед целочисленным autoincrement (ID 1, 2, 3...)?
> **Ответ:** 
> 1. Безопасность: с числовыми ID злоумышленник может легко парсить данные инкрементом (`/tasks/1`, `/tasks/2`). С UUID угадать ID невозможно.
> 2. Распределённость: UUID можно генерировать на клиенте или сервере приложений до вставки в БД, не дожидаясь ответа генератора SEQUENCE базы данных.
> 3. Готовность к шардингу: при объединении данных из разных баз или шардов исключены коллизии первичных ключей.

### В7: Как устроена ротация Refresh-токенов и защита от компрометации?
> **Ответ:** При каждом вызове `/api/v1/auth/refresh` старый refresh-токен немедленно удаляется из БД и Redis, а клиенту выдаётся совершенно новая пара (access + refresh). Если злоумышленник попытается использовать перехваченный старый токен повторно, система обнаружит попытку несанкционированного доступа и отклонит запрос (`401 Token Revoked`).

### В8: Как код защищён от циклических подзадач, если дерево очень глубокое?
> **Ответ:** Перед привязкой родителя вызывается метод [`would_create_cycle`](file:///home/opium/.agy/university_app/app/repositories/task.py). Он использует итеративный обход цепочки предков с сохранением посещённых узлов в `set`. При глубине дерева задач до 100 уровней проверка выполняется за считанные миллисекунды без опасности рекурсивного переполнения стека Python (`RecursionError`).
